1. Topic, Partition & Offset Model

In Kafka architecture, data is organized in a hierarchy ranging from logical stream names down to physical log files stored on disk across cluster brokers.

Understanding Topics and Partitions

A Topic represents a logical stream category (such as order-events or user-logs). A Topic does not exist as a single file on disk. Instead, each Topic is divided into multiple Partitions.

A Partition is the actual physical unit of storage on disk. Each Partition corresponds to a physical directory on a broker's file system (for example: /tmp/kafka-logs/order-events-0/). Dividing a topic into partitions provides two major technical benefits:

  • Scalability: It allows data for a single topic to spread across multiple hard drives and servers in a cluster, rather than being capped by a single machine's storage capacity.
  • Parallelism: It allows multiple consumers in the same Consumer Group to read data from different partitions concurrently without locking or resource conflicts.

Ordering Guarantees

Kafka provides a conditional ordering guarantee: strict message ordering is guaranteed ONLY within the same Partition. Kafka does NOT guarantee message order across different partitions of the same topic.

To preserve order for related events (such as all transactions belonging to the same user ID), producers hash the message key: 

PartitionID = MurmurHash2(Key) % TotalPartitions

Messages sharing the same key are routed to the exact same partition and appended sequentially in strict chronological order.

Understanding Offsets

An Offset is a 64-bit monotonically increasing integer assigned to each record as it is appended to a partition. Offsets are immutable. Once a record is written to a specific offset, that position is never modified or overwritten.

2. Storage Engine & Segment Index (.log / .index)

Kafka's storage engine relies on an append-only commit log architecture. Write speeds reaching hundreds of megabytes to gigabytes per second are achieved by optimizing disk I/O operations at the operating system level.

Disk I/O Optimization (Sequential Write)

Random write operations on hard drives require the read/write head to move across disk platters (Disk Seek), introducing severe latency. Kafka uses only Sequential Append-Only Writes. Sequential writes eliminate disk seek overhead, allowing hard drives to approach RAM-like throughput speeds.

Segment Files Structure

To prevent a log file from growing into hundreds of gigabytes—which makes file management and data cleanup difficult—Kafka splits a partition's log into smaller files called Segments (typically capped at 1GB or 7 days). Each segment file is named after its Base Offset (the offset of the first record in that segment).

Each segment consists of three primary files:

  • .log: Contains the actual raw binary message payload.
  • .index: A sparse index mapping record Offsets to physical Byte Positions inside the .log file.
  • .timeindex: A sparse index mapping Timestamps to Offsets.

Sparse Indexing Mechanism

Unlike traditional databases that index every single row, Kafka uses sparse indexing: an index entry is written to the .index file only after every 4KB of data written to the .log file. 

Lookup workflow for a record at Offset = 105:
1. Binary search on segment file names -> Identify target file 00000000000000000000.log
2. Binary search on 00000000000000000000.index -> Find entry [Offset 100 -> Byte Position 4096]
3. Seek to Byte 4096 in .log file -> Linearly scan a few records -> Stop at Offset 105.

3. Producer Architecture, Routing & Acks Guarantees

Producers are responsible for routing, batching, and transmitting record batches to the correct partition on cluster brokers.

Routing Strategies

  • Explicit Partition: Direct routing to a partition ID explicitly specified in code.
  • Key Hashing: Uses MurmurHash2(Key) % NumPartitions when a record contains a key.
  • Sticky Partitioner: When key is null, the producer sticks to a single partition until its batch is full before moving to the next partition, significantly reducing network fragmentation.

Batching & Compression

Producers group records into a single RecordBatch based on batch.size (default 16KB) and linger.ms. The entire batch payload is compressed (Snappy, LZ4, Gzip, or Zstd) at the producer before transmission over TCP.

Data Reliability (Acks Settings)

Acks Setting Confirmation Mechanism Trade-off Profile
acks = 0 Producer fires data over socket and does not wait for broker response. Lowest latency, highest data loss risk if broker crashes.
acks = 1 Waits for only the Partition Leader to write to local disk. Balanced performance. Data loss possible if Leader crashes before replication.
acks = all Waits for Leader and all ISR replicas to flush record to disk. Zero data loss guarantee (No Data Loss). Higher latency.

4. Consumer Group, Rebalance Protocol & Offset Management

Consumer Groups enable parallel consumption scale-out and automatic failover handling.

Partition Assignment Golden Rule

Each Partition in a topic is assigned to AT MOST ONE Consumer within the same Consumer Group at any given time. If the number of consumers exceeds the number of topic partitions, extra consumers remain idle on standby.

Rebalance Protocol & Heartbeats

Rebalancing is triggered when members join/leave the group or topic partitions change. One broker acts as the Group Coordinator to manage group state transitions.

Consumers continuously send Heartbeat signals to the Group Coordinator. If no heartbeat is received within session.timeout.ms, the coordinator considers that consumer dead and initiates a rebalance.

Offset Commit Storage

Consumer progress is recorded by committing offsets. Kafka stores offset commits inside an internal system topic named __consumer_offsets.

  • At-Most-Once: Offset is committed before message processing. Messages can be lost if worker crashes mid-processing.
  • At-Least-Once: Offset is committed after message processing. Messages can be reprocessed if worker crashes before committing. Requires idempotent consumer logic.

5. Replication Engine, ISR & High Watermark

Kafka's replication engine provides high availability even under physical server hardware failures.

Leader and Follower Replicas

Each partition has a Replication Factor. One replica is elected as Leader to handle all read and write traffic. Remaining replicas act as Followers, continuously sending FetchRequest calls to pull new data from the Leader to local disk.

High Watermark (HW) Mechanism

To maintain strict data consistency across nodes, Kafka tracks these offset metrics:

  • LEO (Log End Offset): The offset of the next record to be written to a specific replica's log.
  • ISR (In-Sync Replicas): The subset of replicas actively keeping up with the Leader.
  • High Watermark (HW): The minimum LEO across all replicas in the ISR: HW = min(LEO_ISR).
Read Safety Constraint: Consumers are strictly allowed to read messages only up to Offset < High Watermark. Messages beyond the HW are uncommitted and unsafe because they have not been fully replicated to all ISR members.

6. KRaft Metadata Consensus Protocol

Starting in version 3.x, Kafka replaced ZooKeeper with KRaft (Kafka Raft Metadata Mode), an in-house consensus protocol.

Limitations of ZooKeeper Architecture

Under ZooKeeper, cluster metadata was duplicated between ZooKeeper and the Kafka Controller, causing state desynchronization under high load. When a controller crashed, the new controller had to reload all metadata from ZooKeeper, pushing failover times up to 30 minutes on large clusters with hundreds of thousands of partitions.

KRaft Architecture

KRaft integrates Raft consensus directly into Kafka brokers. A quorum of Controller nodes elects an Active Controller. All cluster state changes are appended as event records to an internal single-partition topic named @metadata. Controller failover time drops to under one second.

7. Retention Policies vs Log Compaction

Kafka provides two independent cleanup policies to manage long-term disk storage usage.

Log Retention Policy

Deletes old segment files based on time (log.retention.hours) or total partition size (log.retention.bytes). Data deletion always operates on entire segment files rather than deleting individual records inside a log.

Log Compaction Policy

Designed for state store or Change Data Capture (CDC) workloads. Kafka background threads clean old segments by retaining only the latest record (highest offset) for each Key. To signal a complete key deletion, a producer sends a record with Value = null (known as a Tombstone Record).

8. Kafka Wire Protocol & Binary Framing

Kafka's network communication protocol uses custom binary frames encoded in Big-Endian network byte order over persistent TCP connections.

Request Header Frame Layout

+---------------------------------------------------------------+
|                      MessageSize (INT32)                      |
+-------------------------------+-------------------------------+
|        ApiKey (INT16)         |       ApiVersion (INT16)      |
+-------------------------------+-------------------------------+
|                     CorrelationId (INT32)                     |
+---------------------------------------------------------------+
|          ClientId (Length: INT16 + Raw UTF-8 Bytes)           |
+---------------------------------------------------------------+
|                       Request Body ...                        |
+---------------------------------------------------------------+

The CorrelationId field enables asynchronous multiplexing: client applications can send multiple requests concurrently over a single TCP connection without suffering from Head-of-Line blocking.
